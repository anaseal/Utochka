# Аудит архитектуры и план рефакторинга

Дата: 2026-08-13. Ветка: `main`, коммит `8487939`.
Объём: 182 исходных файла, 21 120 строк (`src`, без тестов), 46 тестовых файлов.

**Принцип отбора задач.** В плане нет задач «сделать красиво». Каждая карточка отвечает на вопрос
«что сломается или сколько будет стоить, если этого **не** делать». Задачи, которые не прошли этот
фильтр, вынесены в §7 «Что делать не нужно» — с обоснованием, почему.

## 0. Резюме: что болит на самом деле

Сначала честная часть — **проект написан дисциплинированно**, и «наводить порядок» с нуля не нужно:

- дизайн-токены живут в одном `:root`, каждая шкала прокомментирована с обоснованием;
- утечек памяти нет — все 22 файла с подписками и таймерами снимают их в cleanup (проверено пофайлово);
- слой чистых утилит (`utils/`) покрыт тестами очень плотно — 46 файлов;
- общие механики холста уже вынесены грамотно: `useWeaveCanvas`, `CanvasSurface`, `useColorHighlight`, `useStampTool`, `useThreadTrace`;
- «быстрый путь» рисования (`paintBeadFast` + прямая запись в DOM) и кеш сводки на время мазка — верные решения, сделанные осознанно.

Реальных проблем ровно **две**, и обе системные, а не косметические.

### Проблема A. Ось «техника» не абстрагирована — копипаста растёт линейно

Для каждой из четырёх техник (`silyanka`, `crossWeave`, `peyote`, `loom`) заведён **свой полный
вертикальный срез**: хук проекта, холст, редактор, бисерина, линейки, генератор, зеркало, заливка,
штамп, тема, tool-switch.

Замер идентичности пары Peyote ↔ Loom (сравнение после нормализации имён, без комментариев и пустых строк):

| Файл A | Файл B | Строк | Совпало | Идентичность |
|---|---|---:|---:|---:|
| `usePeyoteProject.ts` | `useLoomProject.ts` | 180 | 180 | **100%** |
| `PeyoteEditor.tsx` | `LoomEditor.tsx` | 142 | 142 | **100%** |
| `PeyoteBeadView.tsx` | `LoomBeadView.tsx` | 86 | 86 | **100%** |
| `PeyoteRulers.tsx` | `LoomRulers.tsx` | 52 | 52 | **100%** |
| `peyoteMirror.ts` | `loomMirror.ts` | 26 | 26 | **100%** |
| `usePeyoteToolSwitch.ts` | `useLoomToolSwitch.ts` | 16 | 16 | **100%** |
| `PeyoteCanvasView.tsx` | `LoomCanvasView.tsx` | 333 | 330 | 99% |
| `peyoteTheme.ts` | `loomTheme.ts` | 23 | 21 | 91% |
| `peyoteStamp.ts` | `loomStamp.ts` | 74 | 66 | 89% |
| `peyoteFloodFill.ts` | `loomFloodFill.ts` | 47 | 40 | 85% |

**≈980 строк дословного клона в одной паре техник** плюс ~190 строк клонированных тестов.

**Цена бездействия, измеримо:** любая правка в поведении прямоугольных техник (штамп, зеркало,
заливка, режим плетения, экспорт PNG) делается дважды и тестируется дважды. Любая забытая
вторая правка — молчаливый баг, который найдёт пользователь, а не CI: тестов у холстов и хуков нет.

### Проблема B. Стоимость взаимодействия линейна по числу бисерин

`BeadGrid` мемоизирован, но его пропсы меняются на каждое действие — `beads.map()` пересоздаёт
React-элемент на каждую бисерину плюс два замыкания-обработчика.

Порядок величин по `generator.ts` и `APP_CONSTRAINTS` (`maxGridWidth: 100`, `maxGridHeight: 30`):

- дефолт (70×4): ~1 900 бисерин → ~6 000 SVG-узлов;
- максимум (100×30, span 10): **~18 000 бисерин → ~50 000 SVG-узлов и ~36 000 обработчиков**.

**Где это чувствуется прямо сейчас** (конкретные сценарии, а не абстрактное «много элементов»):

1. **Драг штампа.** `stampPreviewPatch` пересчитывается на каждое движение указателя
   (`useStampTool` троттлит по кадру — то есть до 60 раз в секунду) и уходит пропом в `BeadGrid` →
   полная пересборка сетки **каждый кадр** всё время, пока пользователь двигает штамп.
2. **Драг подвески из каталога.** `hoveredRow` → `highlightedNodeIds` → `BeadGrid` — тот же эффект.
   (`BeadGrid` выносили в `memo` именно из-за лагов драга — но лечили `hoveredCol`, а `hoveredRow`
   через `highlightedNodeIds` продолжает пробивать мемоизацию.)
3. **Одиночный клик и конец мазка.** `setDesignMap` → новый объект → пересборка всей сетки.

Протяжка карандашом уже обойдена через `paintBeadFast`, и это работает — но обход закрывает
один сценарий из четырёх.

### Чего в проекте нет (и не надо выдумывать)

- утечек памяти;
- хаоса в цветовых токенах (45 hex + 47 rgba на весь `src`, и почти все — графика холста, не UI);
- отсутствия тестов на доменную логику.

## 1. Архитектура и переиспользование компонентов

### 1.1. Главный рычаг: реестр техник вместо union'а

**Сейчас.** Каждый общий компонент знает про все техники поимённо:

```ts
// src/components/Editor/Header/Header.types.ts
export type HeaderProps = SharedHeaderProps & (
  | { technique: 'silyanka';   silyankaProps: SilyankaHeaderProps;   crossWeaveProps?: undefined; peyoteProps?: undefined; loomProps?: undefined }
  | { technique: 'crossWeave'; crossWeaveProps: CrossWeaveHeaderProps; silyankaProps?: undefined; peyoteProps?: undefined; loomProps?: undefined }
  | { technique: 'peyote';     peyoteProps: PeyoteHeaderProps;       silyankaProps?: undefined; crossWeaveProps?: undefined; loomProps?: undefined }
  | { technique: 'loom';       loomProps: LoomHeaderProps;           silyankaProps?: undefined; crossWeaveProps?: undefined; peyoteProps?: undefined }
);
```

```tsx
// Один и тот же блок в Header.tsx, GridSidebar.tsx (и вариация в HeaderToolGroup.tsx)
const silyankaProps   = props.technique === 'silyanka'   ? props.silyankaProps   : undefined;
const crossWeaveProps = props.technique === 'crossWeave' ? props.crossWeaveProps : undefined;
const peyoteProps     = props.technique === 'peyote'     ? props.peyoteProps     : undefined;
const loomProps       = props.technique === 'loom'       ? props.loomProps       : undefined;
```

Это N×M: N техник × M общих компонентов. В `HeaderToolGroup.tsx` кнопка Flood Fill написана
**три раза подряд** ([:118-147](../src/components/Editor/Header/HeaderToolGroup.tsx#L118-L147),
[:139-147](../src/components/Editor/Header/HeaderToolGroup.tsx#L139-L147),
[:199-207](../src/components/Editor/Header/HeaderToolGroup.tsx#L199-L207)) — отличается только
объект-источник пропсов.

**Станет.** Техника описывается один раз — набором возможностей, компоненты спрашивают про
возможность, а не про имя:

```ts
// src/techniques/types.ts
export interface TechniqueCapabilities {
  stamp: boolean;
  stampAnchorEdge: boolean;   // только силянка
  thread: 'none' | 'single' | 'dual';
  mirror: boolean;
  decorTab: boolean;
  weaveSegment: 'row' | 'column' | 'cell' | 'silyanka';
}
```

```tsx
// HeaderToolGroup.tsx — было три копии блока, стала одна
const { capabilities: caps } = useTechnique();

<FloodFillButton active={activeTool === 'flood-fill'} onToggle={...} />
{caps.stamp && <StampButton {...tools.stamp} anchorEdge={caps.stampAnchorEdge ? … : undefined} />}
{caps.mirror && <MirrorMenu {...tools.mirror} />}
```

### 1.2. Presenter / Container: где смешаны слои

Три слоя (`utils` — геометрия, `hooks` — состояние, компоненты — разметка) разделены хорошо.
Слабое место одно: **`CanvasView.tsx`** — 754 физических строки (≈540 по метрике `max-lines`),
87 пропсов, и это одновременно контейнер (12 хуков) и презентер (многослойный SVG).

Шов проходит по слоям декора — они уже отдельные `memo`-компоненты и получают одинаковую четвёрку:

```tsx
<PendantLayer      … isDrawing={isDrawing} highlightedColor={highlightedColor}
```

## 2. Управление состоянием и бизнес-логика

### 2.1. Четыре хука проектов живут одновременно

```tsx
// src/App.tsx:43-46
const silyanka   = useSilyankaProject(settings.palette);
const crossWeave = useCrossWeaveProject(settings.palette);
const peyote     = usePeyoteProject(settings.palette);
const loom       = useLoomProject(settings.palette);
```

Комментарий в коде объясняет причину (Rules of Hooks + сохранение состояния при переключении).
Причина верная, **решение — нет**: три неактивные техники держат по истории Undo (до 30 снимков
`designMap` каждая) и пересчитывают `useMemo` генерации сетки на рендерах `App`.

Аргумент «состояние пропадёт» не выдерживает проверки: всё персистится в `localStorage` через
`usePersistedState`, а `switchTo` в библиотеке проектов вообще перезагружает страницу.

### 2.2. Prop drilling: транзит на 170 строк

`SilyankaEditor` перекладывает `silyanka.*` в `CanvasView` — 70 строк подряд
([:217-288](../src/components/Editor/SilyankaEditor.tsx#L217-L288)), плюс 55 строк в
`PendantsSidebar` и 45 в `GridSidebar`. Это не «много пропсов у компонента», а **транзит**:
`SilyankaEditor` почти ничего из передаваемого не использует.

Следствие важнее объёма кода: `designMap` меняется → новый объект `drawingControls` → рендер `App`
→ **`Header`, `EditorSidebar`, `ProjectGallery` перерисовываются на каждый мазок карандашом**.

### 2.3. Дубли внутри одного хука

В `useSilyankaProject.ts` (611 строк) четыре обработчика построены по одному шаблону —
`handlePendantPaint`, `handleChainPaint`, `handleDecorTailPaint`, `handleToothPaint`
([:526-601](../src/hooks/useSilyankaProject.ts#L526-L601)). Различие — только способ найти
зеркальный элемент. Фабрика вместо четырёх копий даёт −60 строк и одно место для правки
логики зеркальной заливки. **Делать попутно**, отдельной задачи не заслуживает.

## 3. Стилизация и дизайн-токены

Цветовые токены в порядке — трогать не нужно. «Плывёт» другое.

### 3.1. Брейкпоинты: 20 разных условий, шкалы нет

| Условие | Объявлений |
|---|---:|
| `max-width: 767.98px` | 13 |
| `max-width: 599.98px` | 9 |
| `orientation: landscape) and (max-height: 500px` | 5 |
| `max-width: 1024px` | 4 |
| `max-width: 1279.98px` | 3 |
| `max-width: 1149.98px` | 3 |
| `max-width: 720px` | 3 (+2 в составных) |
| `max-width: 479.98px` | 1 |
| `min-width: 768px` / `720px` / `1024px` | по 1 |

`720px` соседствует с `767.98px`, `1149.98` с `1279.98` — без объяснения разницы. Это единственная
часть стилей, которая реально порождает баги: элемент перестраивается на 720, а его сосед — на
767.98, и в промежутке 720–768px верстка разъезжается.

### 3.2. Отступы: 212 литералов дублируют существующие токены

Шкала `--sp-1…5` = 4/8/12/16/24px **уже есть**, но в CSS написаны литералы: `8px` — 91 раз,
`4px` — 44, `12px` — 30, `16px` — 28, `24px` — 19. Плюс вне шкалы: `6px` (60 раз), `14px` (44),
`10px` (32).

Честная оценка: замена литералов на токены **не чинит ни одного бага** и несёт риск визуальных
регрессий. Ценность появляется только при смене шкалы отступов или темы. См. §7 — почему это
не отдельная задача.

### 3.3. Иконки: 115 использований, 9 разных размеров

```
size=9 → 6    size=10 → 3   size=11 → 1
size=12 → 21  size=13 → 13  size=14 → 63
size=15 → 4   size=16 → 3   size=20 → 1
```

`size={14}` — фактический стандарт (63 из 115). `11`, `15`, `20` — по одному-четыре использования,
почти наверняка случайные: разница в 1px между `14` и `15` в соседних кнопках видна как неровный ряд.

## 4. Производительность и чистота кода

### 4.1. Три источника лишней работы, по убыванию эффекта

**(а) Пропсы, меняющиеся каждый кадр, пробивают `memo` у `BeadGrid`.** Это причина сценариев 1 и 2
из §0: драг штампа и драг подвески пересобирают всю сетку 60 раз в секунду.

**(б) Обработчики на каждой бисерине.** Два замыкания на бусину:

```tsx
// src/components/Editor/BeadView/BeadView.tsx
<g onPointerEnter={() => onPointerEnter(id)}
   onPointerDown={(e) => { …; onPointerDown(id); }}>
```

При 18 000 бисерин — 36 000 замыканий, пересоздаваемых при каждой пересборке.

```tsx
// Станет: делегирование — один обработчик на группу
<g className="bead-grid" onPointerDown={handleDown} onPointerOver={handleOver}>
```

⚠️ `pointerenter` не всплывает — при делегировании нужен `pointerover` **и** проверка, что
указатель перешёл на другую бисерину (иначе переход между `<circle>` внутри одной `.bead`
сработает как новое наведение). `releasePointerCapture` обязан остаться на `e.target`, иначе
сломается рисование пальцем ([BeadView.tsx:60-67](../src/components/Editor/BeadView/BeadView.tsx#L60-L67)).

**(в) Разбиение на memo-ряды.** `logicalIndex.row` уже есть у каждой бисерины:

```tsx
const rows = useMemo(() => groupBy(beads, b => b.logicalIndex.row), [beads]);
const rowKeys = useMemo(
  () => rows.map(r => r.map(b => designMap[b.id]).join('|')),  // O(N) строк вместо O(N) элементов
  [rows, designMap],
);
```

`BeadRow` под `memo` перерисуется, только если изменился цвет внутри него.

### 4.2. Рендер всего дерева на каждый мазок

См. §2.2. Важное уточнение к решению: **обернуть `Header` в `memo` сейчас бесполезно** — ему
передаются пересоздаваемые каждый рендер значения (`silyankaProps={{…}}`,
`colorSources={collectColorSources(…)}`, `onToggleReferenceWindow={() => …}`). Сначала контекст и
стабилизация пропсов, только потом `memo`.

### 4.3. Мелочи, которые стоит поправить попутно

- `computeXFloodFill` строит карту смежности заново на каждый вызов и использует `queue.shift()` —
  O(n²) на массиве. Замена `shift()` на индекс-указатель — одна строка.
- `useStampTool` вызывается с `useMemo` прямо внутри литерала аргументов
  ([CanvasView.tsx:537](../src/components/Editor/CanvasView/CanvasView.tsx#L537)) — работает, но
  читается плохо.
- `handleWeaveContextMenu` перебирает все бисерины на правый клик
  ([CanvasView.tsx:522](../src/components/Editor/CanvasView/CanvasView.tsx#L522)) — рядом уже
  построен `beadPositionIndex`.

### 4.4. DRY / SOLID: где нарушено

- **DRY** — §1.1 (980 строк клона), §1.3, §2.3, три копии Flood Fill.
- **OCP** — добавление техники требует правки `Header.types.ts`, `Header.tsx`, `HeaderToolGroup.tsx`,
  `GridSidebar.tsx`, `App.tsx`, `useEditorKeyboardShortcuts.ts`, `useWeaveModePanel.ts`.
- **SRP** — `CanvasView.tsx` (контейнер + презентер + экспорт), `useSilyankaProject.ts` (611 строк).
- **ISP** — `CanvasView` требует 87 пропсов, половина нужна только вложенным слоям.

## 5. Пошаговый план

Порядок выбран так, чтобы каждый шаг был проверяем и не ломал приложение. Ключевая асимметрия:
`utils` покрыт тестами плотно, компоненты — почти нет (тесты есть только у `ErrorBoundary`).
Поэтому движемся снизу вверх, а туда, где тестов нет, сначала приносим тесты.

```
Фаза 1 ── W-01 характеризационные тесты Peyote/Loom      ← страховка для фазы 2
             │
Фаза 2 ── W-02 слияние utils Peyote/Loom (под тестами)
          W-03 useGridProject         (100% клон)

             │
Фаза 3 ── W-06 реестр техник + Header/GridSidebar на capabilities
             │
Фаза 4 ── W-07 контексты проекта (транзит + лишние рендеры)

             │

             │
```

### W-01 · Характеризационные тесты Peyote/Loom

**Зачем.** Единственная страховка для фазы 2. Сейчас у `usePeyoteProject`/`useLoomProject` и
`PeyoteCanvasView`/`LoomCanvasView` тестов нет вовсе — слияние ~980 строк вслепую означает, что
регрессию найдёт пользователь. Побочная польза: после слияния эти же тесты покрывают обе техники
одним набором.

**Зависимости:** нет. **Файлы:** `src/hooks/useGridProject.test.ts`,
`src/components/Editor/CanvasView/GridCanvasView.test.tsx` (новые).

**Сделать.** Тесты, фиксирующие текущее поведение (jsdom — докблок `// @vitest-environment jsdom`
первой строкой, мок `localStorage` из `src/test/localStorageMock.ts`):

1. Хуки: изменение ширины/высоты с учётом Mirror Mode (`shiftXxxDesignMapColumns`),
   `handleFloodFill` в обычном и зеркальном режиме, захват и постановка штампа, `makeSymmetric`,
   `resetGridAll` / `gridIsDefault`, персист под ключами `peyote:*` и `loom:*`.

### W-02 · Слияние `utils` Peyote/Loom

**Зачем.** Убирает четыре пары файлов, где правка обязана делаться дважды. Плюс чинит O(n²) в
заливке — на сетке 100×30 это ощутимо при клике заливкой по большой области.

**Зависимости:** W-01. **Файлы:** `src/utils/{peyote,loom}{Mirror,FloodFill,Stamp,Generator}.ts` →
`src/utils/rectGrid/*.ts`; тесты рядом.

**Контекст (перепроверено чтением файлов).** Различия **не сводятся к префиксу id**:

- `mirror` — идентичны, кроме префикса → `createMirrorId(prefix)`, тривиально;
- `floodFill` — различается правило соседства: Peyote учитывает чётность ряда
  (`r % 2 === 0 ? [c-1, c] : [c, c+1]`), Loom ортогонален (`(r±1,c)`, `(r,c±1)`) →
  параметр-стратегия `neighbors(r, c)`;
- `stamp` — **различаются сигнатуры**: `translatePeyoteBeadId` принимает `anchorRow` и применяет
  `colParityCorrection` (компенсация полушагового сдвига рядов), у Loom этого параметра нет вовсе.
  Слияние — через флаг `parityCorrection: boolean`, а не механическим переименованием.

**Сделать.** Параметризованные утилиты + замена `queue.shift()` на индекс-указатель.

**Приёмка.** Существующие тесты (`peyoteMirror`, `loomMirror`, `peyoteFloodFill`, `loomFloodFill`,
`peyoteStamp`, `loomStamp`, `peyoteGenerator`, `loomGenerator`) проходят **без правок в самих
тестах**, кроме путей импорта. `npm run typecheck` чист.

**Риски.**
- **Средний:** потерять `colParityCorrection` при слиянии штампа — узор Peyote порвётся на
  несвязанные половины при переносе через нечётное число рядов. Снижение: `peyoteStamp.test.ts`
  этот случай покрывает — не менять его.
- **Низкий:** перепутать порядок соседей в заливке — Loom начнёт заливать по диагонали.

**Откат.** Один коммит на файл-пару; откатывается независимо.

**Не трогать.** `mirror.ts`, `floodFill.ts`, `stamp.ts` силянки и `crossWeave*` — другая геометрия.

**Замена 212 CSS-литералов отступов на `--sp-*`.** Не чинит ни одного бага, не ускоряет разработку
(писать `var(--sp-2)` не быстрее, чем `8px`), но требует проверки вёрстки на всех экранах.
Ценность появится, только если понадобится менять шкалу отступов целиком. **Решение:** заменять
попутно, когда файл и так правится по другой причине. Отдельной задачи не заводить.

**Слияние `CanvasView` (силянка) и `CrossWeaveCanvasView`.** Общие механики уже вынесены в хуки
(`useWeaveCanvas`, `CanvasSurface`, `useColorHighlight`, `useThreadTrace`), а различия геометрии
реальны: у силянки пять слоёв декора, NODE/SPAN, per-row span-контролы; у крестика ничего этого
нет. Слияние даст компонент с ветвлением по технике внутри — ровно то, от чего уходим в W-06.
**Решение:** не сливать. Если `CanvasView.tsx` станет неудобным — разделить его на контейнер и
презентер (§1.2), это другая задача и другой выигрыш.

**Разбиение `useSilyankaProject.ts` (611 строк) на три хука.** Файл большой, но связный: сетка,
декор и заливка переплетены через `applyUnifiedFloodFill` и общую историю. Разрезать его без
внешней причины — это перекладывание кода с высоким риском. **Решение:** отложить до момента,
когда появится конкретная задача, которой мешает текущий размер. Фабрику для четырёх
`handleXxxPaint` (§2.3) сделать попутно — она локальна и безопасна.

**Унификация `useSilyankaToolSwitch` с прямоугольным `useRectToolSwitch`.** Проверено чтением:
силяночный сбрасывает пять разных состояний (штамп, цепочка, зубец, hole-segment hover, pending
delete), прямоугольный — только штамп. Общего — одна строка `setActiveTool`. **Решение:** слить
только Peyote+Loom (это часть W-03), силянку не трогать.

**Обёртывание компонентов в `memo` «на всякий случай».** Пока пропсы пересоздаются каждый рендер
(см. §4.2), `memo` только добавляет стоимость сравнения. Мемоизировать — после W-07 и по
результатам Profiler'а, а не превентивно.
